# Drainage Agent 评测策略

## 目的

评测用于验证 Drainage Agent 是否能够在真实排水监测工作流中稳定地产生有数据依据、范围正确、状态安全且可交付审核的结果。运行轨迹记录一次真实任务经过的步骤；测试和 Eval 使用预先定义的场景、状态与断言判断这些步骤和结果是否符合预期。

评测不是把所有能力都交给真实模型重复验证。确定性代码、Web 连通、Agent 单轮决策、跨轮状态和真实端到端流程分别在最合适的测试层验证。

## 五个评测层

### 1. 确定性能力

使用 pytest 验证数据导入、标准化、筛选确认、数据质量、降雨、事件响应、排污规律、RDII、风险、结果新鲜度、项目隔离、后台任务、报告组装、文件安全和持久化。

数值、状态门禁和项目隔离必须由代码强制保证，不能依赖模型自觉。

### 2. Web 前后端连通

使用 FastAPI `TestClient` 验证接口契约，使用确定性的浏览器自动化验证页面操作、接口请求、后端状态和页面反馈组成的闭环。模型调用默认使用可控替身。

Web 连通测试覆盖所有用户可见操作和关键状态转换，但不在浏览器中重复运行完整 Agent 语义题库。

### 3. 单轮 Agent Eval

验证一次用户请求下的意图理解、工具选择、参数提取、数据边界、歧义处理、能力拒绝、结果复用、报告范围和副作用控制。

即使一个请求内部需要串联多个工具，只要用户在一轮中已经完整表达需求，仍属于单轮 Eval。

### 4. 多轮 Agent Eval

只验证依赖历史状态的能力，包括指代消解、后续补参、约束继承、参数修改、要求撤销、增量分析、结果失效、人工确认恢复、报告范围逐步形成和上下文压缩后的长期一致性。

能在单轮验证的工具和边界不在多轮题库中重复铺开。

### 5. 真实端到端验收

使用真实网页、后端、隔离数据和真实模型运行少量关键业务主链，证明各层组合后仍可工作。端到端验收只保留高价值流程，不承担全面语义覆盖。

建议至少包括：

1. 新建项目、导入、映射、筛选确认和旱天分析。
2. 降雨、事件响应、RDII、风险和报告下载。
3. 无数据覆盖时拒绝分析且不产生虚假报告。
4. 多轮修改范围后生成正确报告。
5. 长任务进度查看与取消。

## 场景覆盖方法

单轮和多轮 Eval 使用多维度场景网格设计测试集：

1. 定义会改变用户请求和系统行为的维度及取值。
2. 将不同维度的取值组合为场景元组。
3. 把元组转写为真实自然语言请求或对话。
4. 为工具、参数、回答、产物、状态和禁止副作用定义判定。
5. 运行应用并保存完整 trace。

不生成完整笛卡尔积。每个维度取值必须至少被覆盖，关键维度采用成对覆盖，高风险组合和历史故障保留为回归用例。

详细维度、现有用例处置和新增用例规划见 `EVALUATION_CASE_PLAN.md`。

## 隔离数据和破坏性场景

Eval 使用版本化、只读的测试夹具。每条需要特定数据状态的场景把夹具复制到独立临时监测项目后执行，不修改仓库夹具原件、用户当前项目或其他用例的数据。

夹具至少覆盖：

- 完整有效数据；
- 缺少降雨资料；
- 缺少点位资料；
- 部分点位或时间覆盖；
- 错误字段、类型或单位；
- 极端值和异常时间；
- 损坏或不合规报告模板。

异常数据用于真实验证失败边界。模型服务超时、进程退出、数据库锁定和网络中断等无法由数据稳定触发的故障，放入独立可靠性测试，不通过破坏共享环境制造。

## 判定证据

自动判定优先使用客观证据：

- 工具名称、调用顺序和参数；
- 工具返回状态；
- 项目、会话和运行状态；
- 结果新鲜度与分析身份；
- 文件类型、路径、内容和范围；
- 是否产生未经请求的副作用；
- 最终回答是否与工具证据一致。

表达清晰度、专业解释质量等主观项目使用人工或经过校准的模型判定。关键边界不得只依赖主观判分。

### 当前可观测性

生产运行记录已关联 `run_id`、监测项目、会话、模型、状态、耗时、Token、错误和回复摘要；工具步骤记录名称、参数、状态、耗时、错误和产物。trace 会脱敏敏感字段并限制长文本和大列表。

Eval schema v2 在此基础上额外保存场景维度、隔离环境配置、结构化预期、每轮完整 trace 事件，以及执行前后的文件清单。它可以支持工具选择、参数、错误状态、产物和非预期副作用的客观判定。

当前仍不把完整业务数据、API 密钥或无限长模型正文写入运行记录。表达质量和专业解释仍需要人工判定；模型、网络、进程和数据库级故障需要独立可靠性测试，不能仅由 Agent Eval 代替。

## 建议规模

- 单轮正式集：35 至 45 条。
- 多轮正式集：10 至 15 组。
- CI 冒烟集：5 至 8 条。
- HITL 专项：2 至 4 组。
- 上下文压缩专项：1 至 2 组。
- 真实浏览器端到端流程：3 至 5 条。

## 发布门槛

- 所有确定性单元测试和集成测试通过。
- Web 关键工作流、项目隔离、刷新恢复和关键失败路径通过。
- 无数据编造、跨项目污染、越过人工确认、错误范围报告和虚假产物路径等严重错误为零。
- 关键 Agent Eval 用例全部通过；其他 Eval 达到评测版本定义的通过率。
- 关键 Agent 用例重复运行后保持稳定，而不是偶然通过一次。
- Docker 能从全新环境启动并完成脱敏演示流程。
- Eval 记录模型、Token、耗时、工具调用、错误和产物，并可通过 `run_id` 定位 trace。
- README 能指导陌生用户完成安装和首次分析。

## 运行方式

运行确定性测试：

```powershell
python -m pytest
```

Agent Eval 的用例、运行器、人工标注数据和 HTML 报告位于 `quality/eval/`。需要真实模型调用的完整 Eval 会产生费用，应在评测版本和测试数据固定后手动运行；CI 只运行选定的关键用例。

在不调用模型的情况下验证 schema v2 单轮题库和隔离夹具：

```powershell
python -m quality.eval.eval_stage2.run_eval quality/eval/eval_stage2/cases_single.yaml --validate-only
```

验证 schema v2 多轮题库：

```powershell
python -m quality.eval.eval_stage2.run_eval quality/eval/eval_stage2/cases_multiturn_v2.yaml --validate-only
```

正式运行时显式指定输出文件，避免覆盖历史结果：

```powershell
python -m quality.eval.eval_stage2.run_eval quality/eval/eval_stage2/cases_single.yaml -o quality/eval/eval_stage2/results_single_v2.jsonl
```

每个 Eval 回合记录独立的 `run_id`。评测结果使用该标识定位对应 trace 或项目内 Agent 运行记录，不要求默认保存完整提示词和模型回复。

## 持续评测

GitHub Actions 的 `Quality Gate` 分成两个层级：

- 每次 push 和 pull request 自动运行全量 pytest、单轮/多轮题库结构与隔离夹具验证，并构建 Docker 镜像。这一层不调用外部模型，不依赖密钥，是合并前必须稳定通过的门禁。
- 真实模型 CI 冒烟集通过 `workflow_dispatch` 手动触发。它需要仓库 Secret `AGENT_API_KEY`，可选配置 `AGENT_BASE_URL` 和 `AGENT_MODEL`；运行结束后保存 JSONL 结果与客观检查文件 30 天。

完整 40 条单轮和 15 条多轮评测仍在版本发布前手动运行。日常修改只在线复测受影响场景；历史故障对应的确定性规则必须由 pytest 长期保护。
