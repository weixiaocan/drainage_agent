# 下一版本候选 Issues

本文记录 v1.0 发布后发现、但不在当前版本立即修改的产品与工程问题。每个 Issue 在进入开发前仍需完成设计确认；本文不代表功能已经实现。

## VNEXT-001：项目内历史会话管理

### 状态

- 状态：待规划
- 来源：v1.0 使用复盘
- 类型：产品能力、会话生命周期
- 优先级：下一次专门升级时评估

### 问题

当前系统已经把 Agent 会话持久化到 SQLite。清空工作区时，活动会话的 `history_json` 和 `state_json` 也会转存到 `archived_agent_sessions`。

但是 Web 只有当前会话入口，没有历史会话列表。用户清空后无法查看、选择或继续旧对话，因此归档数据目前只具有潜在的审计和排障价值，没有形成可使用的产品能力。

实际使用方式更接近 Codex 等对话式工作台：用户会先判断本次准备处理什么问题，再选择新建对话，或者进入某条相关的旧对话继续追问。

### 核心产品判断

监测项目与对话不是一对一关系，而是一对多关系：

```text
监测项目
├── 会话 A：数据质量与筛选
├── 会话 B：降雨事件与 RDII
├── 会话 C：旱天规律与风险
└── 会话 D：报告生成与修改
```

- 项目负责承载数据、分析基线、结果和报告。
- 会话负责承载某个问题的对话历史及其 `SessionState`。
- 用户可以在同一项目内创建多条会话。
- 用户可以重新进入旧会话，并基于该会话的历史和状态继续提问。
- 新建会话不应删除或归档其他会话。
- 清空工作区与会话管理必须是两个不同操作。

### 用户故事

作为排水监测分析人员，我希望查看当前项目下的历史会话，以便找到以前讨论过的问题。

作为排水监测分析人员，我希望根据标题、时间和摘要识别会话，以便选择正确的上下文继续追问。

作为排水监测分析人员，我希望新建一条空会话，而不影响项目数据、分析结果和其他历史会话。

作为排水监测分析人员，我希望重新进入旧会话后恢复其对话历史和工作状态，以便继续未完成的分析。

作为排水监测分析人员，我希望删除不再需要的会话，并明确知道该操作是否可以恢复。

### 建议交互

Web 对话区增加会话侧栏或会话选择器，至少提供：

- 新建会话
- 当前项目的历史会话列表
- 切换会话
- 会话标题与最后更新时间
- 删除或归档会话

会话标题可以先使用首条用户消息截断生成。是否使用模型生成标题，应在实现阶段单独评估，不能阻塞基本能力。

项目切换后只显示目标项目的会话。不得展示或加载其他项目的会话。

### 生命周期语义

需要在实现前统一以下操作的含义：

| 操作 | 对话 | SessionState | 项目数据与结果 |
|---|---|---|---|
| 新建会话 | 保留旧会话，创建新会话 | 创建空状态 | 保留 |
| 切换会话 | 加载目标会话 | 加载目标状态 | 保留 |
| 归档会话 | 从默认列表隐藏，可在归档区查看 | 保留 | 保留 |
| 删除会话 | 按确认后的策略删除或软删除 | 同步处理 | 保留 |
| 清空工作区 | 现有会话如何处理需明确确认 | 不得静默复用失效状态 | 清除筛选、分析和报告等派生状态 |
| 删除项目 | 删除该项目全部会话 | 删除 | 删除 |

`SessionState` 中可能引用筛选文件、事件、结果或报告。恢复旧会话时不能盲目恢复这些引用，必须校验它们是否仍属于当前项目、是否存在、是否因数据或分析基线变化而失效。

### 数据与接口设计约束

- 会话必须继续绑定 `project_id` 和 `batch_id`，禁止跨项目恢复。
- 活动与归档状态应成为会话自身的可查询字段，避免依靠在两张表之间搬运数据表达生命周期。
- 会话至少需要标题、创建时间、最后更新时间和归档状态。
- 历史列表接口不应返回完整 `history_json`，只有打开某条会话时才加载详情。
- 服务端数据库是会话事实来源；浏览器 `localStorage` 只能作为界面缓存，不能决定会话是否存在。
- 数据或分析基线改变后，应保留旧对话文本，但将失效的结构化状态明确标记为不可继续使用或进行安全降级。
- 删除、归档、恢复和工作区清空必须留下可测试的确定性行为。

### 验收标准

1. 用户可以在一个项目下创建至少两条独立会话，并在二者之间切换。
2. 切换后，右侧显示目标会话的正确历史，下一条消息使用目标会话的 `SessionState`。
3. 刷新页面或重启服务后，历史会话列表和当前选择仍可恢复。
4. 项目 A 的会话不会出现在项目 B 中，也不能通过修改请求参数跨项目加载。
5. 新建会话不会删除、归档或修改旧会话。
6. 归档会话不会参与新会话推理，但用户可以在归档入口查看。
7. 恢复一条仍然有效的旧会话后，可以继续上下文追问。
8. 底层数据或分析基线变化后，恢复旧会话不会复用已经失效的筛选、分析或报告状态。
9. 清空工作区前，界面明确说明对项目数据、派生结果和会话的影响。
10. 永久删除项目后，该项目的活动会话和归档会话均不可访问。

### 测试范围

- Repository：创建、列出、重命名、归档、恢复和删除会话。
- API：项目隔离、无效会话、归档状态和并发更新时间。
- Web：新建、切换、刷新恢复、归档入口和删除确认。
- 集成测试：会话历史与 `SessionState` 一起恢复。
- 安全测试：跨项目 session ID 不可读取。
- 回归测试：清空工作区、替换数据和修改分析基线后，不得复用失效状态。
- Agent Eval：从旧会话继续追问时，显式约束和必要上下文仍然成立。

### 本 Issue 暂不包含

- 跨项目共享会话。
- 多用户、权限和协作。
- 对所有历史会话建立向量检索或自动长期记忆。
- 自动把一条会话中的结论注入其他会话。
- 云端同步与跨设备同步。
- 用模型自动合并或拆分会话。

### 开发前待确认

- “清空工作区”是否保留全部会话为只读历史，还是要求用户选择处理方式。
- 会话删除采用软删除还是永久删除，以及默认保留期限。
- 数据变化后，旧会话只读展示还是允许清除失效状态后继续。
- 是否需要导出历史会话，用于审计、排障或 Eval 数据沉淀。
