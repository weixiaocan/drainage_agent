# Drainage Agent 架构审计

## 审计目标

本审计将成熟开源版本的产品规格映射到现有代码，判断哪些模块应保留、哪些模块需要加深，以及新能力应放在哪些接缝。目标是增量重构并持续保持测试通过，不重写已经验证的排水分析算法。

本文使用以下术语：

- **模块**：具有一个接口和一套实现的代码单元。
- **接口**：调用者正确使用模块所需知道的全部内容。
- **接缝**：可以替换行为而不修改调用位置的地方。
- **适配器**：在接缝处满足接口的具体实现。
- **深度**：调用者通过较小接口获得较多行为的程度。

## 当前结构

当前主调用链为：

```text
Web / CLI
  -> Agent 编排与对话守卫
  -> Agent 工具包装
  -> 确定性分析
  -> 文件、manifest、图表和报告
```

现有系统已经具备 138 项自动化测试、Agent Eval、Docker 构建、结构化 trace 和完整的排水分析工具。主体功能不是需要被替换的原型，而是需要建立稳定产品接缝的存量系统。

## 应保留的深模块

### 确定性分析模块

`analysis.modules` 中的数据筛选、数据质量、降雨、事件响应、排污规律、RDII 和风险分析以 DataFrame 为主要输入输出。调用者不需要了解内部计算步骤，现有测试能够直接验证领域结果。

**判断**：保留算法和主要函数接口。项目化改造通过输入上下文适配这些函数，不把项目、数据库、Web 或 Agent 状态引入算法实现。

### 报告组装器

章节导向的报告组装器已经把模板扫描、事实构建、章节渲染、校验和 DOCX 保存隐藏在一个入口后，并具有专门测试。

**判断**：保留其内部实现，将外部接口进一步收窄为一个报告请求和一个报告结果。不要让上层继续传递十余个彼此关联的参数。

### 运行轨迹

现有 trace 已能以 JSONL 记录运行和工具事件，并对大结果做摘要。

**判断**：保留事件记录实现，在其上增加按项目、批次和运行查询的接口；默认隐私规则继续位于该模块内部。

## 需要加深的模块

### Agent 工具包装

当前工具包装文件同时承担：

- 参数规范化；
- 数据覆盖守卫；
- 筛选确认；
- 缓存键与报告数据缓存；
- manifest 新鲜度；
- 图表绘制；
- CSV、Excel 和 DOCX 落盘；
- 报告所需分析补齐；
- 工具状态与错误转换。

它虽然只向 Agent 暴露少量工具，但内部职责缺乏局部性。相同的项目路径、结果身份、缓存和落盘规则分散在大量辅助函数中。

**目标**：建立一个深的分析运行模块。外部接口接受标准化分析请求并返回分析结果；模块内部统一处理前置条件、调用确定性算法、结果身份、复用、版本、落盘和轨迹。Agent 工具只做参数模型到分析请求的适配。

不要先机械地把大文件切成多个小文件。只有新接口经过垂直工作流验证后，旧辅助函数才迁入新模块。

### Agent 编排

当前 Agent 核心同时负责：

- 模型创建和工具注册；
- trace；
- 长对话压缩；
- 报告范围的自然语言规则；
- 筛选确认恢复；
- 直接报告执行；
- 会话约束状态。

报告范围规则和筛选状态在 Agent 外围直接拦截模型，保障了现有行为，但也让一个模块了解工具实现、会话细节和报告参数解析。

**目标**：建立一个对话运行模块，接口只接收当前项目、当前分析批次、会话和用户消息。确定性的等待输入、等待确认和状态恢复由工作流状态决定；LLM 负责意图理解和工具选择，不拥有项目事实。

现有守卫在迁移完成前继续保留，不能先删除再依赖提示词替代。

### Web 入口

当前 Web 入口直接持有一个全局依赖对象、一个全局 Agent 和内存会话字典。上传操作直接写入共享数据目录并清空共享 manifest。

**删除测试**：如果删除 Web 入口中的文件和状态逻辑，这些复杂性会立即扩散到每个路由，因此当前入口没有形成足够深的模块。

**目标**：Web 仅调用项目、批次、导入、作业、对话和结果模块的接口。路由不拼装磁盘路径，不直接清空 manifest，不保存领域状态。

### 路径与会话依赖

当前路径对象把整个部署映射为一套固定数据、输出、工作和日志目录；会话状态同时保存降雨事件、筛选确认、运行状态和多种缓存。

**目标**：用明确的项目上下文和分析批次上下文替代全局路径。会话只保存对话所需状态，分析事实和作业状态持久化到 SQLite。

## 新增的深模块

### 项目仓库

**接口职责**：

- 创建、列出和读取监测项目；
- 创建和读取分析批次；
- 创建派生分析批次并校验冲突；
- 返回某批次的隔离工作空间。

SQLite 和临时 SQLite 都属于本地可替代依赖，不需要公开数据库端口。测试跨越项目仓库接口，使用临时数据库和临时文件目录。

### 数据导入

**接口职责**：

- 检查原始监测数据并返回导入预览；
- 应用已确认的字段与单位映射；
- 生成标准数据和校验结果；
- 保存和复用导入配置。

确定性识别是内部实现。LLM 是真正外部依赖，只在确定性规则无法识别时通过一个候选映射接口注入；生产使用 OpenAI 兼容适配器，测试使用固定响应适配器。

### 分析运行

**接口职责**：

- 接收一个包含项目、批次、分析类型、范围和参数的分析请求；
- 验证资料、标准数据和分析基线等前置条件；
- 计算完整分析身份；
- 复用新鲜结果或生成新版本；
- 返回统一状态、摘要、数据和产物。

这是工具、Web 作业和测试共同跨越的主要分析接缝。现有确定性分析函数位于其实现内部。

### 本地作业

**接口职责**：

- 提交耗时分析；
- 查询作业状态和进度；
- 标记完成或失败；
- 在应用重启后恢复为可解释状态。

第一版只有本地执行适配器，不创建外部队列端口。只有将来出现第二个真实执行适配器时，才引入新的外部接缝。

### 报告生成

**接口职责**：

- 接收报告范围、模块、已计算事实和模板选择；
- 校验占位符契约；
- 生成并校验 DOCX；
- 返回报告、综合表和人工补充模块提示。

现有报告组装器成为其内部实现。报告模块不负责重新解释用户自然语言，也不直接查找全局文件。

### 运行记录

**接口职责**：

- 记录带项目、批次、会话和运行身份的结构化事件；
- 查询一次运行的步骤、耗时、Token、错误和产物；
- 应用默认脱敏和调试模式规则。

JSONL 可以作为第一版事件存储，SQLite 保存可查询索引。Web 运行记录页面只读取此接口。

## 依赖分类与接缝

| 依赖 | 分类 | 设计 |
|---|---|---|
| 排水分析计算 | 进程内 | 直接位于分析运行模块内部 |
| SQLite | 本地可替代 | 测试使用临时 SQLite，不公开多余端口 |
| 文件系统 | 本地可替代 | 测试使用临时目录 |
| 本地后台执行 | 进程内 | 第一版不创建外部队列端口 |
| OpenAI 兼容模型 | 真正外部 | 定义模型调用接口，生产与测试使用不同适配器 |
| Docker 与服务器 | 部署环境 | 通过容器验收和健康检查验证 |

## 主要差距

| 产品规格 | 当前状态 | 差距 |
|---|---|---|
| 多监测项目 | 单一全局路径 | 缺少项目仓库和隔离工作空间 |
| 多分析批次 | 上传覆盖共享文件 | 缺少批次身份、历史和派生关系 |
| 引导式数据导入 | 固定别名自动识别 | 缺少预览、确认、单位映射和导入配置 |
| 分析基线 | CLI 确认机制已存在 | Web 缺少下载、重传、校验和持久状态 |
| 工作台与对话 | 以聊天页为主 | 缺少项目、批次、作业和结果视图 |
| 后台作业 | 同步请求 | 缺少持久作业状态和进度 |
| 结果版本 | 内存缓存与单 manifest | 缺少批次级完整分析身份和历史版本 |
| 规范化模板 | 固定模板与自由结构并存 | 缺少占位符契约和上传校验 |
| 可观测页面 | JSONL trace | 缺少查询索引、Token/耗时完整记录和 Web 查看 |
| 完整 CI/CD | pytest、Eval 和镜像构建基础 | 缺少版本镜像、Demo 部署、健康检查和回滚 |
| 开源发布 | 尚无正式发布基线 | 缺少许可证文件、发布清单和当前 README |

## 重构顺序

1. **建立项目仓库和分析批次工作空间**：先让两个项目能够创建、切换并隔离文件，不改变分析算法。
2. **建立数据导入模块**：让一个批次从原始监测数据生成经确认的标准数据。
3. **建立分析运行模块**：把现有一个核心分析垂直迁入新接缝，验证结果身份、复用和版本。
4. **迁移筛选确认工作流**：把待确认与已确认状态从内存会话迁入批次状态。
5. **扩展到全部现有分析和报告**：按垂直工作流逐个迁移，旧接口在迁移期间保持兼容。
6. **加入本地后台作业和工作台进度**：先覆盖一个耗时分析，再扩展其他任务。
7. **加深报告生成模块**：实施占位符契约，收窄报告接口并移除旧自由模板路径。
8. **完善运行记录与 Eval 关联**：让一次 Web 运行可从界面定位到工具、错误和产物。
9. **完成发布链路**：许可证、README、版本镜像、公开 Demo、健康检查和回滚。

每一步都必须形成可演示的垂直行为并保持现有测试通过。不要先进行横跨全仓库的目录重排。

## 测试策略

- 主要验收接缝仍是 Web 用户工作流，使用真实 SQLite、真实临时文件目录和可控模型适配器。
- 确定性算法继续通过现有输入输出测试验证，不把测试迁入 Web 层。
- 新分析运行模块建立后，缓存、前置条件、版本和落盘测试应从旧辅助函数迁到新接口；替换完成后删除重复的浅层测试。
- Agent Eval 验证自然语言与多轮编排，不承担项目隔离、数据一致性或数值正确性测试。
- 第一个垂直切片必须同时验证两个项目，防止在单项目数据上误以为隔离已经成立。

## 明确不做

- 不重写已验证的排水分析算法。
- 不因文件较大就机械拆文件。
- 不为 SQLite、文件系统或本地作业创建只有一个适配器的假接缝。
- 不先引入 Redis、Celery、Kafka、PostgreSQL 或前端框架。
- 不在新接口稳定前删除现有筛选守卫、缓存和报告路径。
