# Drainage Agent 产品规格

## Problem Statement

排水监测分析人员需要把来自不同系统的流量、液位、流速、降雨和点位资料整理为可分析的数据，确认旱天筛选结果，执行多种确定性分析，制作图表并编写模块化报告。即使操作熟练，从原始资料到报告初稿最快仍需约三个工作日，大量时间消耗在重复的数据整理、计算、制图和文字组织上。

现有 Drainage Agent 已经具备主要分析工具、CLI、基础 Web、报告生成、测试和 Eval，但仍以单一全局数据目录和同步对话为中心。它缺少面向外部使用者的数据导入确认、多监测项目与多分析批次隔离、稳定的后台任务、结构化工作台、完整可观测性和可重复发布流程，因而尚不能作为成熟的开源应用交付。

## Solution

将 Drainage Agent 建设为作品集级成熟开源 AI 应用。排水监测分析人员通过 Web 项目工作台创建监测项目和分析批次，上传原始监测数据，确认字段与单位映射，获得标准数据，再确认自动生成的筛选结果，使其成为后续分析共同使用的分析基线。用户可以通过 Agent 对话表达分析意图，由确定性工具完成数据检查、旱雨天分析、RDII、风险评估、图表和报告初稿生成。

第一版以提高效率为首要价值：Agent 支持范围内的报告初稿目标在四小时内形成；包含人工补充模块、修改和审核的完整交付报告目标在一个工作日内完成。Agent 不承担最终专业判断，报告初稿必须经过排水监测分析人员审核后才能成为交付报告。

项目以 Apache License 2.0 开源。正式用户通过 Docker 在个人电脑或可信内网自行部署，不提供 SaaS、多账户或多租户服务。项目同时持续部署一个仅使用脱敏演示数据、严格限制资源消耗的公开 Demo，用于展示完整 CI/CD 能力。

## User Stories

1. 作为排水监测分析人员，我希望通过 Docker 安装 Drainage Agent，以便不配置复杂开发环境就能开始使用。
2. 作为排水监测分析人员，我希望在首次启动时配置 OpenAI 兼容模型，以便使用自己选择的服务和密钥。
3. 作为排水监测分析人员，我希望系统明确展示已验证模型，以便了解哪些模型完成过端到端质量验证。
4. 作为排水监测分析人员，我希望创建命名的监测项目，以便分别管理不同的排水监测任务。
5. 作为排水监测分析人员，我希望查看和切换已有监测项目，以便在一次部署中处理多个项目。
6. 作为排水监测分析人员，我希望每个监测项目的数据和结果相互隔离，以便避免不同项目之间的数据污染。
7. 作为排水监测分析人员，我希望在监测项目中创建分析批次，以便针对指定点位和时段开展一次独立分析。
8. 作为排水监测分析人员，我希望新分析批次不覆盖旧批次，以便保留历史分析依据和结果。
9. 作为排水监测分析人员，我希望选择多个分析批次创建派生分析批次，以便明确开展跨批次分析。
10. 作为排水监测分析人员，我希望跨批次数据出现点位和时间冲突时系统停止合并，以便由我选择可信来源。
11. 作为排水监测分析人员，我希望上传流量监测数据创建常规分析批次，以便开始核心分析流程。
12. 作为排水监测分析人员，我希望按需补充降雨、点位信息和报告模板，以便启用依赖这些资料的能力。
13. 作为排水监测分析人员，我希望缺少某项选填资料时仍能创建批次，以便先完成不依赖该资料的分析。
14. 作为排水监测分析人员，我希望请求依赖缺失资料的分析时收到上传提示，以便补齐输入后继续。
15. 作为排水监测分析人员，我希望原始监测数据保持不变，以便随时核对数据来源。
16. 作为排水监测分析人员，我希望系统识别常见编码、表头、时间、点位、指标和单位，以便减少人工整理工作。
17. 作为排水监测分析人员，我希望看到字段映射、单位换算和标准数据预览，以便在分析前检查识别结果。
18. 作为排水监测分析人员，我希望系统对确定的映射自动处理，以便减少不必要的确认步骤。
19. 作为排水监测分析人员，我希望无法确定的字段或单位必须由我确认，以便防止系统根据数值猜测。
20. 作为排水监测分析人员，我希望 LLM 只为陌生格式提出候选映射，以便利用 AI 降低配置成本而不让它直接改变数据。
21. 作为排水监测分析人员，我希望保存导入配置，以便后续同类文件复用字段和单位规则。
22. 作为排水监测分析人员，我希望分析工具只读取经过确认的标准数据，以便不同工具使用统一输入。
23. 作为排水监测分析人员，我希望运行数据质量检查，以便了解收集率、缺失、异常和数据覆盖范围。
24. 作为排水监测分析人员，我希望系统自动生成筛选结果并解释保留或剔除原因，以便快速检查候选有效数据。
25. 作为排水监测分析人员，我希望下载筛选结果进行修改，以便使用 Excel 完成专业调整。
26. 作为 Web 用户，我希望重新上传修改后的筛选结果并通过结构校验，以便把它确认为分析基线。
27. 作为 CLI 用户，我希望修改本地筛选文件后确认继续，以便复用现有命令行工作方式。
28. 作为排水监测分析人员，我希望系统在我确认筛选结果前暂停后续分析，以便错误不会传递到所有下游结果。
29. 作为排水监测分析人员，我希望确认后系统复用现有筛选结果而不是重新筛选，以便我的人工修改得到保留。
30. 作为排水监测分析人员，我希望分析降雨日和降雨场次，以便选择需要研究的降雨事件。
31. 作为排水监测分析人员，我希望分析指定事件的监测点响应，以便比较流量、液位、流速和响应时间。
32. 作为排水监测分析人员，我希望计算指定事件和点位的 RDII，以便评估降雨入流入渗。
33. 作为排水监测分析人员，我希望分析旱天排污规律，以便识别典型曲线、异常波动和运行特征。
34. 作为排水监测分析人员，我希望评估旱天和雨天风险，以便发现淤积、运行和溢流风险。
35. 作为排水监测分析人员，我希望执行少量点位或时间范围的临时统计，以便处理固化工具之外的长尾问题。
36. 作为排水监测分析人员，我希望系统拒绝缺少拓扑数据的上下游和管网结构结论，以便避免编造专业分析。
37. 作为排水监测分析人员，我希望选择报告范围、时间、点位、事件和模块，以便生成符合任务目标的报告初稿。
38. 作为排水监测分析人员，我希望使用稳定的内置报告模板，以便开箱即用地生成 DOCX 初稿。
39. 作为排水监测分析人员，我希望上传遵循占位符规范的自定义报告模板，以便适配单位 Logo、页眉页脚和章节顺序。
40. 作为排水监测分析人员，我希望上传时校验自定义模板并获得可操作的错误提示，以便修正不兼容模板。
41. 作为排水监测分析人员，我希望所有报告数字来自确定性计算结果，以便 LLM 不会生成未经计算的数据。
42. 作为排水监测分析人员，我希望报告明确标识人工补充模块，以便后续完成空间拓扑关系分析。
43. 作为排水监测分析人员，我希望下载报告初稿、图表和分析表格，以便进行修改、审核和交付。
44. 作为排水监测分析人员，我希望相同分析身份默认复用已有结果，以便减少等待时间和模型费用。

## Implementation Decisions

- 正式产品入口是 Web；CLI 作为开发、调试和高级用户入口保留。
- Web 采用项目工作台与 Agent 对话的混合界面。工作台管理确定性状态，对话处理分析意图、工具编排、解释和追问。
- 第一版采用单机自部署，不提供应用内登录、SaaS、多账户、多租户或多人协作。使用者应在个人电脑或可信内网运行；公网保护由部署者负责。
- 一个部署实例支持多个监测项目。每个监测项目包含多个独立分析批次，项目和批次身份贯穿请求、会话、任务、文件、结果和轨迹。
- 新上传数据创建分析批次，不自动追加、去重或覆盖旧批次。跨批次分析创建派生分析批次，并保留来源关系。
- 派生分析批次遇到相同点位和时间的重复或数值冲突时停止合并，由工程师选择来源。
- 原始监测数据不可变。统一导入流程完成编码识别、字段映射、类型转换、单位统一和质量校验，经工程师确认后生成标准数据。
- 确定性别名和规则优先完成映射；LLM 只能在规则无法确定时提出候选映射。单位缺失、冲突或不明确时不得根据数值猜测。
- 导入配置保存稳定数据来源的字段、单位和解析规则。后续分析工具只使用标准数据。
- 流量监测数据是常规分析批次的必需输入；降雨、点位信息和报告模板按分析目标选填。缺少资料时仅禁用依赖能力。
- 自动生成的筛选结果必须由排水监测分析人员确认后成为分析基线。CLI 支持编辑本地文件后确认，Web 支持下载、编辑、重新上传和结构校验。
- 筛选确认是正式工具状态。确认绑定筛选结果身份；继续后复用已确认文件，不得隐式重新筛选。
- 现有数据质量、降雨、事件响应、排污规律、RDII、风险、临时统计和报告能力构成第一版冻结的业务范围。
- 空间拓扑关系相关的两个报告模块属于人工补充模块。Agent 不得在缺少拓扑数据时生成上下游、管段关联或管网结构结论。
- 内置报告模板是稳定能力。自定义 DOCX 必须遵循公开的占位符契约，系统不承诺解析或复刻任意 Word 文档。
- 报告文字可由 LLM 辅助生成，但所有数值只能来自确定性计算结果。报告初稿必须经工程师审核后才能成为交付报告。
- 完整分析身份由输入数据、分析基线、规范化参数和算法版本组成。身份一致时默认复用结果；明确重跑或任一部分变化时创建新版本。
- SQLite 保存监测项目、分析批次、导入配置、文件索引、筛选确认、结果索引、会话、作业和轨迹索引等结构化元数据。
- 按项目和批次隔离的文件系统保存原始监测数据、标准数据、筛选文件、分析产物、报告和日志。
- 数据库和项目文件目录通过 Docker 持久卷保存。第一版不提供应用内项目 ZIP 导出与恢复。
- 耗时任务使用有限并发的本地后台作业执行器，并持久化任务状态。第一版不引入 Redis、Celery、Kafka 或外部消息队列。
- 读取、可重复分析和生成新产物可以直接执行。修改分析基线、覆盖、删除和清空等状态变更必须绑定具体目标进行明确确认。
- 模型通过 OpenAI 兼容接口配置。只有完成端到端测试的模型列为已验证模型，其他兼容模型不作效果承诺。
- 结构化本地运行轨迹记录项目、批次、会话、运行、模型、工具、参数摘要、状态、耗时、Token、错误和产物。
- API 密钥永不记录，原始监测数据、完整提示词和完整模型回复默认不记录；深度调试记录由用户主动开启。
- 公开 Demo 与正式自部署产品使用同一核心应用，但采用脱敏演示数据、受限权限、低成本已验证模型、缓存、限流、预算熔断和定时重置。
- CI 在提交和 Pull Request 上运行确定性测试、关键离线 Eval 和 Docker 构建。需要真实模型和费用的完整 Eval 在发布前手动运行。
- Continuous Delivery 发布 GitHub Release 与版本化 Docker 镜像；Continuous Deployment 将通过门槛的主分支部署到公开 Demo，并执行健康检查和失败回滚。
- 项目以 Apache License 2.0 发布。公开前检查演示数据、模板、字体、图片和依赖的分发许可。
- 第一版容量验证目标为 50 个点位、30 天、1 分钟采样，约 216 万条记录。半年数据只做压力探索并记录边界，不承诺商业级大数据性能。
- Agent 支持范围内的报告初稿目标在四小时内形成；含人工补充、修改和审核的完整交付报告目标在一个工作日内完成。

## Testing Decisions

- 主要产品验收接缝是 Web 用户工作流。测试从创建监测项目和分析批次开始，经过数据上传、映射确认、筛选确认、后台分析、结果查看和报告下载，验证用户可观察行为。
- Web 工作流测试使用真实的 SQLite、项目文件隔离、服务和后台作业状态，运行在临时环境中；模型调用使用可控替身，以保证快速、稳定和无费用。
- 确定性分析接缝直接覆盖标准化、筛选、数据质量、降雨、事件响应、排污规律、RDII、风险和报告组装，使用固定数据精确比较数值和产物。
- Agent Eval 接缝覆盖自然语言意图识别、工具与参数选择、多轮上下文、筛选确认、报告范围、无数据拒绝、越界能力拒绝和长期约束保持。
- 关键 Eval 用例必须全部通过；非关键 Eval 总通过率至少达到 90%。完整真实模型 Eval 在发布前手动运行并保留结果。
- 所有确定性单元测试和集成测试必须通过，Docker 必须能从全新环境启动并完成脱敏演示流程。
- 多项目测试必须证明两个项目和两个批次不会共享输入、分析基线、结果、会话或作业状态。
- 数据导入测试覆盖常见编码、别名、未知字段、缺失单位、单位冲突、无效时间、空数据和导入配置复用。
- 筛选测试覆盖暂停、下载修改、重新上传校验、确认身份、确认后复用和输入变化后失效。
- 派生分析批次测试覆盖无冲突合并、重叠检测、数值冲突、来源选择和来源记录。
- 后台作业测试覆盖排队、运行、成功、失败、重启恢复、并发上限和取消或超时后的可解释状态。
- 结果复用测试覆盖完整分析身份一致、参数变化、基线变化、算法版本变化和明确重跑。
- 报告测试覆盖内置模板、合规自定义模板、缺少占位符、错误占位符、模块选择、数值来源和人工补充模块提示。
- 安全测试覆盖路径穿越、恶意文件名、不允许的文件类型、未确认状态变更、Demo 上传限制和下载目录边界。
- 可观测性测试覆盖关联标识、工具步骤、耗时、状态、错误、Token 和产物，同时断言密钥与默认禁止内容不会写入轨迹。
- 性能验证使用合成数据测试 50 个点位、30 天、1 分钟采样，并记录导入、筛选、核心分析的耗时和峰值内存。
- 发布验证包括 README 冷启动演练、版本化镜像启动、持久卷重建验证、Demo 健康检查和回滚演练。
- 测试应断言外部行为和领域结果，不绑定内部类、私有函数或具体文件布局。新增测试优先沿用现有 Web TestClient、确定性分析测试和 Eval 运行器。

## Out of Scope

- SaaS 托管服务、应用内账号、组织、角色、权限和多租户计费。
- 多人实时协作、评论、审批流和报告签发。
- Redis、Celery、Kafka、分布式任务、多服务器调度和商业级高并发。
- 任意 DOCX 结构理解、像素级模板复刻和不符合占位符规范的自由报告生成。
- 自动完成空间拓扑关系、上下游、管段关联和管网结构分析。
- 替代工程师作出最终专业判断、自动签发或直接对外交付报告。
- 自动猜测未知字段、缺失单位或冲突数据。
- 新增第一版冻结清单之外的排水分析算法。
- 自动合并新上传数据、静默去重、默认采用最新数据或覆盖旧分析结果。
- 应用内完整项目 ZIP 导出、跨部署恢复向导和云端备份服务。
- 对半年连续数据提供明确性能承诺，或为此引入大数据基础设施。
- 保证所有 OpenAI 兼容模型具有相同的工具调用和报告质量。
- 公开 Demo 接收用户文件、保存永久项目或提供正式生产用途。
