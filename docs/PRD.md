# 排水监测数据分析 Agent - 产品需求文档 (PRD)

> 版本: v0.1
> 日期: 2026-06-10
> 状态: 待 review
> 前置项目: 排水监测数据分析 Pipeline（已完成，8 个模块可独立运行）

## 1. 项目背景与定位

### 1.1 业务背景

现有系统是固定顺序的 Pipeline：8 个分析模块按预设流程一次性跑完，产出完整报告。但真实使用中，分析需求是碎片化、多样的：

- 只做旱天分析，看某几个点位的特征曲线
- 只统计某场降雨的事件响应
- 只看风险分析结果
- 临时需求：单独看哪些天因缺失率被剔除、把某个点位的液位单独画出来

固定 Pipeline 无法响应这种灵活性——要么全跑（浪费），要么手动单模块调试（门槛高）。本项目将 Pipeline 升级为**分析 Agent**：用户用自然语言提需求，Agent 自主决定调用哪些分析能力、按什么顺序调用、何时向用户确认。

### 1.2 项目定位

| 优先级 | 定位 | 说明 |
|--------|------|------|
| 主 | 简历旗舰项目 | 求职 AI 应用工程师的核心作品，优先架构清晰、设计决策可讲述 |
| 次 | 工作工具 | 自己及同事日常使用，优先稳定可用 |
| v2 | 可分发产品 | 分发给排水行业同仁，v1 仅在设计上不堵死这条路，不为其投入开发 |

时间压力下的取舍原则：**先保简历项目所需的核心机制完整跑通，再保工具好用度**。

## 2. 术语表

| 术语 | 定义 |
|------|------|
| 模块 (Module) | 现有 Pipeline 中的 8 个分析单元（data_filter、rainfall_analysis 等），已有可工作的代码 |
| 固化工具 (Module Tool) | 将模块包装成的 Agent 工具，逻辑经过验证、输出格式稳定，对应高频标准需求 |
| 通用编程工具 (run_python) | Agent 可调用的代码执行工具，Agent 现场编写 Python 代码处理长尾灵活需求 |
| 探查工具 | describe_data / list_results，让 Agent 了解当前数据和已有结果的状态 |
| 前置检查 | 每个固化工具执行前校验所依赖的中间结果是否存在，不存在则返回结构化错误 |
| 后置参数 | 只能在上游结果产生后由用户选择的参数（典型：降雨场次编号），由参数缺失驱动 Agent 询问 |
| 质量提醒 | Agent 摘要关键中间结果、对异常主动提示的行为——系统提示词约定的判断，非硬性断点 |

## 3. 范围定义

### 3.1 v1 范围（本次必做）

| # | 功能 | 是否含 LLM | 说明 |
|---|------|-----------|------|
| 1 | Agent 核心循环 | 是 | 多轮对话，自主选择工具、处理工具返回、决定下一步 |

| 5 | 依赖恢复机制 | 是（由 Agent 决策） | 工具返回"缺少前置结果"错误，Agent 自主补跑前置分析 |
| 6 | 对话式参数采集与质量提醒 | 是 | 后置参数（如场次）由 Agent 询问采集；关键中间结果向用户摘要、异常时主动提醒；用户可声明免确认直跑 |

| 10 | 项目记忆 | 是（Agent 决定记什么） | 质量提醒环节的确认结论、用户纠正与偏好写入 PROJECT_NOTES.md，跨会话不重复询问 |

### 3.2 明确不做的功能

## 4. 用户与使用场景

### 4.1 用户

- 主要用户：开发者本人及环境工程同事（懂业务，不懂代码）
- 次要用户（v2）：排水行业同仁

### 4.2 典型使用场景

**场景 A：标准分析需求（走固化工具）**

1. 用户将监测数据放入 data/ 目录，启动 CLI
2. 用户："分析一下 3 月份各点位的旱天流量特征"
3. Agent 调 describe_data 了解数据 → 调 run_dry_analysis → 收到"缺少筛选结果"错误 → 自主调 run_data_filter
4. 筛选完成后，Agent 摘要关键数字（有效/剔除天数、主要剔除原因），发现异常（如剔除比例过高）时主动提醒并建议调整方向
5. 用户认可后，Agent 完成旱天分析，告知特征曲线图位置并摘要曲线形态

**场景 B：长尾灵活需求（走 run_python）**

1. 用户："单独看一下哪些天因为缺失率被剔除了，统计各点位的剔除天数"
2. Agent 判断无现成工具对应 → 调 run_python，现场编写代码读取筛选结果、统计、输出表格
3. 代码报错时，Agent 读取错误信息自行修正重试
4. Agent 以表格形式回复统计结果

## 5. 功能需求详述

### 5.1 Agent 核心循环

- **输入**：用户自然语言指令（CLI 多轮对话）
- **核心逻辑**：维护对话历史；每轮由 LLM 决策（直接回答 / 调用工具 / 向用户提问确认）；工具结果回填上下文后继续决策，直到任务完成
- **输出**：自然语言回复 + 产物文件位置
- **含 LLM**：是（编排决策核心）
- **验收标准**：场景 A、B 端到端跑通；单轮任务中连续工具调用 ≥3 次不丢失目标

### 5.2 探查工具

**describe_data**
- 输入：无参数（或可选点位/时间过滤）
- 逻辑：扫描 data/ 目录，返回点位列表、时间范围、采样频率、缺失概况；格式不符时返回具体哪一项不符
- 输出：结构化摘要（供 Agent 阅读，非给用户的最终文案）
- 含 LLM：否

**list_results**
- 输入：无参数
- 逻辑：扫描 outputs/，返回已存在的分析结果清单（哪些 sheet、哪些图、生成时间），并比对 data/ 当前状态，为每项结果标注是否过期
- 输出：结构化清单
- 含 LLM：否
- 验收标准：Agent 在调用任何固化工具前，能依据这两个工具的返回判断"数据是否就绪、哪些分析可复用"

### 5.3 固化工具（8 个）

每个工具是对现有模块 `run()` 的薄包装，统一遵循：

- **前置检查**：执行前校验依赖的中间结果文件是否存在；缺失时不执行，返回结构化错误，格式统一为 `{"status": "blocked", "missing": "<前置结果名>", "hint": "请先调用 <工具名>"}`；前置结果存在但已过期（早于数据更新）同样返回 blocked，提示重跑
- **参数**：暴露两类——用户维度（时间范围、点位、输出内容选择）+ 分析阈值（可选参数，带默认值，如缺失率阈值、雨天判定阈值）。Agent 仅在用户明确要求时填写阈值，否则走默认值。路径、密钥类环境配置永不作为工具参数
- **结果摘要**：执行成功后返回简短结构化摘要（关键数字 + 产物路径），不返回完整数据——完整数据留在 Excel 中，Agent 需要细节时用 run_python 去读
- **含 LLM**：工具本身不含；pattern_analysis 的规律分类、report_assembler 的结论文字沿用既有 LLM 调用

依赖关系（写入各工具描述，不写成集中调度代码）：

| 工具 | 前置依赖 |
|------|----------|
| run_data_filter | 无 |
| run_rainfall_analysis | 无 |
| run_dry_analysis | 筛选结果 |
| run_event_stats | 降雨场次分析 + 用户选定场次 |
| run_pattern_analysis | 旱天分析 |
| run_rdii_analysis | 旱天分析 + 降雨场次分析 |
| run_risk_analysis | 监测数据（细化依赖在包装时按模块实际确认） |
| run_report_assembler | 拟纳入报告的各模块结果 |

- **验收标准**：每个工具单独被 Agent 调用一次成功；任一工具在缺前置时返回 blocked 错误且 Agent 能据此补跑

### 5.4 通用编程工具 run_python

- **输入**：Agent 生成的 Python 代码字符串
- **核心逻辑**：在受约束的执行环境中运行代码；捕获 stdout/stderr 与异常完整返回给 Agent，供其自我修正
- **目录约束**：可读 data/ 与 outputs/；写入仅允许 workspace/ 目录，禁止覆盖固化工具的标准输出文件
- **执行约束**：超时上限（建议 60s）、禁止网络访问
- **预置环境**：pandas、numpy、matplotlib 可直接 import
- **含 LLM**：代码由 Agent（LLM）现场生成
- **验收标准**：场景 B 跑通；代码首次报错后 Agent 能在 ≤2 次重试内自行修正常见错误（路径、列名）

### 5.5 对话式参数采集与质量提醒

不存在任何硬性断点机制——对话的回合制本身就是控制权交还。原 Pipeline 的 3 个介入点按性质归入两类行为：

**后置参数采集**（原介入点2）：
- 场次编号只能在降雨分析完成后选择。Agent 跑完上游分析后列出场次清单（编号、起止、雨量、等级），询问用户选定，作为参数传给下游工具
- 通用规则：工具所需参数缺失且无默认值时，由参数缺失驱动询问

**质量提醒**（原介入点1、3，系统提示词约定的判断行为）：
- 产出被下游依赖的结果后，Agent 向用户摘要关键数字（有效/剔除天数及比例、特征曲线形态等）
- 指标异常时主动指出并建议调整方向（阈值、时间范围、剔除点位）；用户不满时以新参数重跑
- 用户可随时声明"免确认直接跑完"，Agent 即不再中途询问；也可要求"每步给我看"——伸缩性由对话控制

**验收标准**：场景 A 中筛选摘要实际发生且用户回复能改变后续行为；声明免确认后 Agent 一路执行到底不再询问

### 5.6 CLI 对话界面

- 启动命令进入多轮对话；支持随时退出
- Agent 回复中的产物用文件路径明确标注
- 不做：富文本渲染、图片内嵌显示（用户自行打开 PNG）

### 5.7 项目记忆（PROJECT_NOTES.md）

- **记录内容**：质量提醒环节的确认结论、用户的纠正与偏好（如"#5 点位在泵站下游，曲线平坦属正常"、"阈值用 0.15"）、项目特有知识
- **机制**：Agent 通过 record_note 工具追加写入；CLI 启动时将整个文件注入系统提示词；文件为人类可读 markdown，用户可直接编辑
- **不记录**：对话流水、分析结果本身（结果归文件系统 + 来历元信息管）
- **验收标准**：跨会话用例——会话 1 中用户给出某纠正/偏好，重启后会话 2 中 Agent 直接应用，不重复询问

## 6. LLM 使用边界

### 6.1 用 LLM 的环节及理由

| 环节 | 理由 |
|------|------|
| Agent 编排决策 | 需理解自然语言需求、动态选择工具与顺序、从错误中恢复——规则无法穷举 |
| run_python 代码生成 | 长尾需求无法预先穷举为固化工具，唯有现场编程能覆盖 |
| 排污规律分类（既有） | 需结合曲线形态做模式归类与文字描述 |
| 报告结论文字（既有） | 自然语言生成 |

### 6.2 不用 LLM 的环节及理由

| 环节 | 理由 |
|------|------|
| 8 个模块内的全部数值计算、阈值判断、统计、绘图 | 输入是纯数值，规则可精确处理，LLM 只会引入不确定性 |
| 前置检查 | 文件存在性判断，纯规则 |
| 数据格式校验 | 列名/类型比对，纯规则 |

### 6.3 LLM 调用的工程化要求

- 模型通过配置切换（沿用既有 OpenAI 兼容封装思路），不与具体厂商绑死
- Agent 决策与工具内 LLM 调用（分类、报告文字）使用相互独立的配置项
- 所有 LLM 调用记录日志（输入摘要、工具调用序列），便于调试与作品集展示

## 7. 配置与交互

- 配置面只剩一个 .env：密钥 + 模型接入点（Agent 决策模型与内核 LLM 各一组）
- 目录路径为仓库固定约定（data/、outputs/、workspace/）；分析阈值为工具签名默认值，可在对话中临时覆盖；不存在 config.yaml 与 baseinfo.xlsx
- 数据接入约定：用户将符合既有格式规范的数据放入 data/ 对应位置即可，无需改代码；格式规范以 Pipeline 现有文档为准

- [ ] 场景 B 端到端跑通（含报错自我修正）

**阶段二（全模块接入）：**

- [ ] 其余 6 个固化工具接入，每个工具至少一条自然语言指令验证通过

- [ ] 一条跨多工具的复合需求验证通过（如"分析 5 月 12 日那场雨的 RDII 情况"，涉及降雨分析 → 场次选择 → 旱天分析 → RDII）

**工程化验收：**

- [ ] 任一工具抛出异常不导致 Agent 进程崩溃，错误信息回到对话中
- [ ] README 包含：架构图、两层工具体系的设计说明、运行方式

## 9. 风险与开放问题

### 9.1 已识别风险与缓解

| 风险 | 缓解 |
|------|------|
| 模型工具调用可靠性不足（选错工具、参数幻觉） | 工具描述写清使用时机与反例；工具数量已控制（12 个）；摘要而非全量数据回填上下文 |
| run_python 误操作文件 | 目录约束 + 禁写标准输出文件；强沙箱明确推迟到 v2 |
| 8 个工具一次性接入导致问题难定位 | 强制两阶段开发顺序，阶段一验证模式后再批量复制 |
| 上下文膨胀（多轮 + 多工具结果） | 工具返回摘要化；完整数据走文件系统 |

### 9.2 待后续确认的开放问题

- Agent 决策用哪个模型（DeepSeek / Kimi / 其他），工具调用能力需实测——开发阶段实测决定
- （已决，详见 ARCHITECTURE.md）框架选型：Pydantic AI；场次选择：对话中收集后作为工具参数传入，无文件同步
