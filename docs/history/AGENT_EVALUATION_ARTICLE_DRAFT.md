# 我怎么给这个排水监测分析 Agent 做评估测试

这篇复盘记录一件具体的事：我怎么给一个排水监测分析 Agent 建立评估体系。

项目能读取监测数据，完成数据筛选、降雨分析、事件响应、RDII、排污规律、风险评估和报告生成。功能逐渐跑通后，我遇到的新问题是：每个计算模块都正确，Agent 仍然可能把整件事做错。

## 一、Agent 测试多了一层决策

普通数据分析程序的输入和调用路径通常是确定的。给定一份数据和一组参数，我可以检查计算结果、文件格式和异常处理。

Agent 在这层之上又多了一次决策。用户只说一句自然语言，它要判断调用哪个工具、参数是什么、是否缺少信息，以及什么时候应该停止。

比如用户要求分析某场降雨的 RDII。RDII 是降雨导致的入流入渗量，工具需要先找到降雨场次，再确认对应点位在这个时段有没有监测数据。

即使 RDII 公式完全正确，Agent 仍可能选错场次。它也可能在没有流量数据时继续计算，最后给出一段看似完整的解释。

多轮对话又增加了一层状态。用户前面限定只看旱天和三个点位，十几轮后再说“看一下风险”，这些限制仍然要保留。

因此我把测试拆成两部分：

- **工具级测试**负责数值、文件和确定性边界。
- **Agent 级评估**负责工具选择、参数、停止条件、跨轮状态和产物范围。

**能写成确定性规则的部分交给代码测试，需要理解自然语言和上下文的部分交给 Agent 评估。** 两套测试各自守住一层。

## 二、工具迁移先守住计算口径

这个 Agent 不是从空白开始写的。项目原来有一套排水监测分析流水线，我需要把其中的能力迁移成 Agent 可以调用的工具。

迁移时最危险的情况，是新代码输出了一张结构相似的表，但计算口径已经变了。结果能运行，数字也像真的，普通冒烟测试很难发现。

我把既有流水线的输出当作基准，逐项比较新工具。比对内容包括：

- **数据质量**：记录数、理论记录数、监测天数和收集率。
- **数据筛选**：缺失率、近零值、异常日、雨天剔除和最终有效点位日。
- **降雨分析**：事件起止时间、总雨量、历时、峰值强度和连续窗口雨量。
- **事件响应**：液位、流量、流速及单位换算后的统计结果。
- **排污规律**：分类、时变化系数、波峰数量、诊断字段和特征曲线。
- **RDII**：总量、过程线、基线流量和图片输出路径。
- **报告**：章节、表格、图片、时间范围和配套工作簿。

这里确实发现过 AI 迁移代码时简化计算逻辑的问题。一次重构把原有流水线压缩成通用的分组统计和简化筛选，代码量明显减少，但原有业务筛选口径没有完整保留下来。

后续的对齐提交删除了这套通用筛选和聚合实现，让工具重新使用既有 `data_filter` 的计算规则。测试也不再只检查“有没有返回表格”，而是检查事件窗口、字段、单位和具体数值。

例如降雨事件测试会核对总雨量 7.5 mm、历时 5 小时、峰值强度 3.0 mm/h，以及 3 小时和 6 小时最大雨量。事件响应测试会核对流量从 L/s 换算到 m³/d 后的结果。

**迁移测试不能只看接口形状。业务口径必须逐项对齐旧系统。** 否则重构越简洁，越可能把专业计算一并删掉。

## 三、单轮评估从主导失败开始收敛

工具级结果对齐后，我把评估重点转向 Agent 的编排。早期单轮评估用了 26 条真实问题，首轮人工判定通过 11 条、失败 15 条。

我没有提前设计失败分类。每条失败只标记“第一处失败”，也就是最早让这条任务偏离正确路径的位置。

标注积累起来后，11 条失败落在同一类：Agent 在分析特定降雨事件或时间窗口前，没有确认点位是否有数据覆盖。这一类占当时失败的 73%。

我只修这一类，并连续复测。A 类失败经历了三级收敛：

| 阶段 | 修改 | 剩余失败 |
|---|---|---:|
| 起点 | 尚未处理覆盖检查 | 11 |
| 提示词 | 要求分析前调用数据检查 | 6 |
| 工具守卫 | 无覆盖时返回需要补充输入 | 1 |
| 执行层守卫 | 报告路径也经过同一覆盖门禁 | 0 |

收敛曲线是 **11 → 6 → 1 → 0**。

这个过程比一次修完更有价值。每轮只改变一个主要因素，我能看到这一层修复究竟解决了多少问题，也能看见剩余失败为什么没有消失。

正式单轮题库后来扩展到 40 条。它覆盖数据质量、临时统计、降雨、事件响应、RDII、风险、排污规律、组合分析、报告、结果复用、能力边界和强制重跑。

每条用例不只写一句问题，还记录场景、维度、预期工具、禁止工具、参数、产物和判定方法。最终人工判定为 **40/40 通过**，最终客观检查没有失败项。

## 四、多轮评估只测跨轮状态

能在单轮测掉的问题，我没有再放进多轮题库。多轮评估只保留必须依赖历史状态的能力。

当前正式集有 **15 组、72 轮**。它覆盖指代消解、后续补参、参数替换、要求撤销、结果失效、范围逐步形成、无覆盖约束保持和上下文压缩。

一条多轮用例会记录每一轮的输入、工具调用、回答、状态变化和运行轨迹。评估器还会保存模型、参数、Token、文件清单和运行编号，失败后可以回到对应轨迹定位。

多轮测试也修正过评测标准本身。M012 中，用户说“再看一次”，Agent 复用了参数相同且仍然有效的结果，但旧判定强制要求重复调用工具。

产品规则要求有效结果直接复用，测试却要求重新计算。这里应该修改评测契约，继续检查点位、事件和旱天范围有没有丢失。

M013 是另一种情况。Agent 记住了 W1 全月结果和 W6 三天结果，却直接比较两个不同时间范围的数值。

这属于真实产品缺陷。修复后，Agent 会先说明两组结果不具备直接可比性，再请求统一时间口径。

最终多轮评估为 **15/15 通过**，没有待标注项。

## 五、开放编码让我少改了很多无关问题

开放编码的做法很简单：逐条阅读结果，只标第一处失败，不预设分类。相似问题自然聚到一起后，再统计频次。

我每轮只处理频次最高的一类。这样可以找到驱动多条失败的共同根因，也能避免同时修改提示词、工具和报告代码，最后无法判断是哪一项起作用。

这个方法也保留了模型波动的空间。一次没有调用预期工具，不一定代表实现回归；它可能已经复用了有效结果，也可能只是一次模型行为波动。

**先看轨迹和产物，再判断失败属于产品、模型还是评测器。** 自动分数只是一条证据。

## 六、客观检查和人工判定各管一部分

工具名、参数、状态、文件路径和报告章节都有明确答案。这些内容适合自动检查。

当前客观检查器会读取评测结果、运行轨迹和产物，检查：

- 必须调用和禁止调用的工具是否符合契约。
- 无数据覆盖时是否仍然生成分析结果。
- 单一任务是否误调无关分析工具。
- 部分范围是否污染综合工作簿。
- 报告是不是 Word 文件。
- 特征曲线图是否真的插入报告。
- 模板占位文本和虚假点位是否残留。
- 未选择的章节是否被裁掉。
- 报告时间是否等于真实数据边界。
- 报告与综合表名称是否配对。
- 窗口内降雨事件编号是否从 1 连续排列。
- 筛选等待人工确认后是否真的停止。

表达是否清楚、解释是否专业、风险描述是否过度，这些内容没有稳定的机械答案。我保留人工判定，也没有引入另一个大模型代替人评分。

为了降低人工负担，我把回答、预期、工具调用和产物放在同一个 HTML 页面里。人工只需要选择通过、失败或不确定，并填写必要的原因。

**客观检查负责可重复的事实，人工负责需要语境的质量。** 两者不能互相替代。

## 七、五次以为在 A 结果在 B

### 提示词让模型检查却不能让它服从

我先在提示词里要求 Agent 分析前检查数据覆盖。复测后，检查动作确实增加了，但 Agent 查出无数据后仍会继续调用分析工具。

提示词改变了行为倾向，没有形成强制边界。无覆盖门禁随后被放进代码。

### 工具入口有守卫仍然会被绕过

守卫进入工具包装层后，11 条 A 类失败只剩 1 条。最后一条来自报告生成路径。

报告生成器直接调用内部实现，没有经过 Agent 工具入口。守卫只有下沉到真正执行计算的那一层，才能覆盖全部调用方。

### 压缩条数正确但摘要内容错了

长对话压缩后，历史消息从 31 条降到 13 条。触发次数和条数都符合预期，但摘要凭空增加了 W4 和一个时间范围。

完整摘要进入轨迹后，来源才清楚。约束提取器扫描了系统提示词，示例里的 W4 被误当成用户约束。

修复后，约束只从用户消息提取。用户没有明确限定的内容会记录为“未明确”。

### 自动判分全通过也可能只是判官太弱

收敛后的产物都正确，判分器没有现成的失败样本。只看全通过无法证明它能发现缺陷。

我复制正确产物，再人为删除曲线图、加入不存在的 W21、修改报告时间、让部分范围写入综合表，并把降雨章节塞进旱天报告。这些缺陷都被抓到，正确产物没有被误报。

**判分器也属于被测代码。** 缺陷注入证明了它真的能识别历史问题。

### needs_input 只是状态不等于真正停止

工具返回 `needs_input` 后，提示词要求模型停止。运行层并没有终止本轮，模型理论上仍能继续调用工具。

人工确认流程把这个差距照了出来。筛选工具的 `needs_confirmation` 后来通过控制异常实现硬停，也说明覆盖守卫的 `needs_input` 需要同样的控制流保护。

“需要输入”描述的是业务状态，“立即停止”属于控制流。两者需要分别实现。

## 八、现在这套评估体系

项目当前有五层测试，每层回答一个不同的问题。

| 层级 | 当前规模 | 主要验证内容 |
|---|---:|---|
| 确定性测试 | 277 个 pytest | 数值、状态门禁、项目隔离、Web 接口、报告和文件安全 |
| Web 连通 | 纳入 pytest | 页面操作、接口请求、后端状态和页面反馈 |
| 单轮 Agent 评估 | 40 条，人工 40/40 | 意图、工具、参数、边界、拒绝、结果复用和产物范围 |
| 多轮 Agent 评估 | 15 组，15/15 | 指代、补参、约束继承、参数修改、失效和长上下文 |
| CI 冒烟 | 3 条发布基线 | 数据质量、无覆盖门禁和报告范围 |

每次 push 和 pull request 会自动运行 277 个 pytest、验证单轮和多轮题库，并构建 Docker 镜像。这部分不调用外部模型。

真实模型评估会产生费用，也会受到网络和模型波动影响。CI 冒烟通过 GitHub Actions 手动触发，完整 40 条单轮和 15 组多轮测试放在发布候选阶段运行。

这套分层让我不再用一次总通过率回答所有问题。计算错了看 pytest，工具选错看单轮轨迹，约束丢了看多轮状态，报告错了直接检查产物。

评估推进到这里，我最看重的也不是“全部通过”四个字。每个通过结论都能回到一条用例、一次工具调用和一个真实产物。
