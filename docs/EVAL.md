# 评估方法与结果

本文件记录排水监测数据分析 Agent 的评估过程。它不是运行日志,而是这个项目如何用评估驱动质量收敛的完整记录:每一轮发现了什么失败、判断根因在哪、改在哪一层、改完用数字验证降了多少。

数值核心(各分析模块的计算结果)已与既有的监测数据分析流水线逐项比对一致,因此本评估的重点不在"算得对不对",而在 **Agent 的编排与产物质量**:它有没有选对工具、有没有在该停时停、长对话里有没有忘掉约束、报告是不是按用户要的范围生成。

---

## 一、评估方法

整套评估遵循同一个循环,而不是"跑一次看通过率":

1. 用真实问题跑 Agent,收集完整 trace(工具调用序列 + 最终回答 + 产物)。
2. 人工开放编码(open coding):逐条标注"第一处失败",先不预设分类法。
3. 标注到一定量后,相似的失败自然聚成几类,统计每类频次。
4. 只修频次最高的那一类,改完复跑、重判,量化这一类降了多少。
5. 客观、可机械判定的失败,沉淀为自动断言;主观质量判断保留人工。

这套循环里有几个反复印证、也反复纠正我的判断,单列在第六节。

评估分两个阶段:**单轮**(测单点功能正确性)与**多轮**(测跨轮状态与报告)。两套用例分工互补,单轮的不被多轮取代——单轮作为回归基线保留。

## 二、单轮评估:数据覆盖前置检查的三级收敛

单轮用例 26 条,首轮人工判定 **通过 11 / 失败 15**。

把 15 条失败按"第一处失败"聚类,**11 条(73%)指向同一个根因**:Agent 在对某个特定降雨事件或时间窗口做分析(事件响应、RDII、事件级风险)之前,没有先确认该时段相关点位是否有数据覆盖;更严重的是,无覆盖时它不说"没数据",而是猜一个"可能的原因"。其余 4 条是零散的标签、过度承诺、指令遵循问题,频次低,归入待办。

这一类(记为 A 类)的修复经历了三级,每一级都由前一级复跑暴露的新失败推动:

| 阶段 | 修复 | A 类通过 / 11 | 关键发现 |
|---|---|---|---|
| 起点 | — | 0 | 11 条全挂在"没做覆盖检查就分析" |
| 一级 | 提示词路由规则:分析前必须先 `check_data` | 5 | 检查率到了,但执行率没到——Agent 现在会查,查出无覆盖却仍继续调分析工具 |
| 二级 | 覆盖守卫焊进分析工具:无覆盖返回 `needs_input` | 9 | 残留 1 条:报告生成路径直接调 `_impl`,绕过了工具包装层的守卫 |
| 三级 | 守卫下沉到执行层 + 报告按覆盖 gate 章节 | 11 | A 类归零 |

收敛曲线:**11 → 6 → 1 → 0**。

这一段得到两个判断,后续反复用到:

- 提示词能让 Agent"去查",但无法强制它"遵守查出来的结果"——确定性的前置约束必须焊进代码,不能靠模型自觉。
- 焊还要焊在**逻辑真正执行的那一层**。守卫挂在工具包装层时,报告组装走的是内部 `_impl` 调用,从下面绕过了守卫。任何能绕过边界直接调内部逻辑的调用方,都会漏掉边界上的守卫。

## 三、多轮评估:报告从流水线到可组合

单轮只测"一句话对不对",多轮测的是状态如何跨轮传递。为此重写了 runner:逐轮携带 `message_history`、逐轮捕获工具调用与回答、记录可复现元数据(模型、参数、时间、token、用例版本)。

多轮用例 16 条,通过数一路 **8 → 10 → 12**〔核对各轮具体数〕,最终收敛。

**多轮状态处理本身是稳的**:指代消解、上下文携带、增量请求都通过;长程一致性用例里,"全程只看旱天"的约束守过了第 7 轮、"限定 W1/W6/W18"守过了第 6 轮,没有漂移。失败集中在另一处。

**主导失败是报告生成仍是写死的全量流水线**(8 条失败中 5 条):无论用户要什么范围,`generate_report` 总是全网全时段重算、只出一种报告;而且它从"综合分析结果"工作簿取数,导致"报告取数"和"落盘规则"耦合——单点/时间窗分析不进工作簿,报告就没料可组装、退回全量。

报告改造的设计落点:

- 报告拆成**取数 + 排版**两步。排版用固定模板,样式恒定;变的只是内容范围。
- `generate_report` 接受三个范围参数:点位、时间窗、章节。**全量 = 三参数全默认**,与单点报告走同一条代码,不再分叉。
- 取数改为"按范围拿分析结果",复用本会话已算结果、未命中才即时跑;**不再读综合表文件**。这一步把报告灵活性与落盘机制彻底解耦。

报告改造后,失败从"架构问题"降级为一批报告装配实现 bug:特征曲线图未插入、模板占位文本与不存在的点位名泄漏进真报告、章节未按选择裁剪、格式输出成 markdown 而非文档、文件名过长、降雨事件编号未按窗口重编。逐条修掉,并为每条补可机械判定的断言。

期间落盘规则也随之演进了三步,核心是"综合分析结果"这个文件的角色定义:

| 版本 | 落综合表的条件 | 问题 |
|---|---|---|
| 初版 | 全网分析就落 | 单点结果覆盖、污染全网底稿 |
| 二版 | 全网 **且** 全时段才落 | 仍把综合表当"完整底稿",但报告灵活性需要它 |
| 终版 | **只在生成报告时**,把进入该报告的模块结果落综合表 | 综合表 = 该报告的数据附件,与报告一一对应、可对照 |

## 四、自动判分:把重复的客观判定交给机器

评估迭代到后期,绝大多数人工判定是在重复确认早已认识的失败模式。这部分应该自动化,人只看需要质量判断的少数。

`quality/eval/check.py` 读取一次运行的 results 与产物,对每条用例跑一组客观断言:覆盖守卫是否生效、是否过度调用无关工具、部分范围是否误写综合表、报告是否为文档格式、是否含特征曲线图、是否含模板占位文本或不存在的点位名、章节是否按选择裁剪、报告时间段是否等于真实数据首末日、综合表命名是否与报告配对、窗口内降雨事件编号是否连续。

**判官本身必须先验证准不准**,否则就是早期那个"全部判通过"的弱判官的翻版。由于收敛后的产物已全部通过、没有真实失败样本,改用**注入测试**验证:基于正确产物,逐条人为造出历史上判过的那类缺陷,确认每一类都能被抓到。

| 注入的缺陷 | 命中断言 | 结果 |
|---|---|---|
| 删掉报告里一张特征曲线图 | `report_has_independent_curve_images` | 抓到,无误报 |
| 报告塞入不存在的点位名 W21 | `report_no_placeholders_or_fake_sites` | 抓到,无误报 |
| 报告时间段改成筛选后错范围 | `report_period_matches_real_data_bounds` | 抓到,无误报 |
| 构造"部分范围却写综合表"的 trace | `partial_scope_no_combined_xlsx` | 抓到,无误报 |
| 只要旱天的报告里留一个降雨章节 | `report_excludes_unselected_sections` | 抓到,无误报 |
| 未破坏的正确产物 | 无 | 无误报 |

六类注入全部抓到、零误报后,`check.py` 接进复跑流程:跑完 eval 自动出客观判分。此后改动复跑,客观回归立即显形,无需逐条人工看。

## 五、上下文压缩:验证它没压坏关键状态

长对话会累积历史直到超出上下文预算。用 pydantic-ai 的 `history_processor`(`capabilities=[ProcessHistory(...)]`)加了最小压缩机制:超过阈值时把早期历史压成一段摘要,摘要里单独保留一块"已确立的约束/偏好"。

压缩做完不能只看结果,要先确认**它真的触发了**——否则"约束没被压坏"可能只是因为压缩从没发生。所以在压缩函数里加了计数与摘要全文记录。临时压低阈值后确认:`history_compaction` 触发,条数 31 → 13。

随后用长程一致性用例验证,发现一个 bug:压缩摘要的约束块里,点位集合从用户立的 `W1/W6/W18` 变成了 `W1/W4/W6/W18`,还凭空多了时间窗。

定位的关键是**先补观测、再动手**:先把压缩摘要全文记进 trace,看见约束块的真实内容,才发现被压缩的对话内容里根本没有 W4——它来自 `system.md` 里的示例文本("部分点位排污规律(如 W4/W6)"、示例文件名里的日期)。根因是约束提取把整个被压缩内容(含 system prompt 示例)拼起来正则扫描,把"对话里出现过的实体"当成了"用户确立的约束"。

修复:约束只从用户消息提取,且只在明确限定语气下提取;用户没立的约束写"未明确",绝不从任何地方抓实体填充。修复后,摘要约束块回到 `W1/W6/W18`、时间窗为"未明确",压缩后第 18 轮的工具调用也回到 `points=["W1","W6","W18"]`。另一条长程用例里同源的 W4 污染也一并消失。

这一段的教训:压缩是会改写上下文的黑盒操作,不能只记条数、不记内容。若当时直接改摘要逻辑,会改错地方——W4 不在对话内容里,在 system prompt 里。先让黑盒现形,才定位到了真正的根因。

## 六、人工确认环节:把"停下来等人"焊进代码

真实使用中,筛选后的数据在用于后续分析前,人工大概率要先看一眼、甚至手动修改。所以需要一个确认环节:`data_filter` 跑完后暂停,等人确认或修改筛选结果,再继续分析。

设计采用"工具返回待确认状态、本轮停住、下一轮继续"的方式,而不是运行时阻塞——后者在同步调用和批量评估下会卡死。

**关键在于"停"必须是代码强制,不能靠提示词。** 这一点直接来自单轮 A 类的教训:提示词能让模型倾向于停,但无法保证它停。本版本 pydantic-ai 没有"某个工具返回后立即结束本轮"的现成入口,于是用控制异常实现:`data_filter` 返回 `needs_confirmation` 后,工具记录层抛出一个自定义异常,被 `run_sync` 外层捕获、直接返回待确认结果。异常从工具执行直接冒出,模型在物理上没有机会继续调用后续分析工具。这是控制流层面的硬停,不是提示词约束。

为避免"每次用筛选结果都停"的反复打断,确认是**按筛选结果的身份**做的,不是按使用次数:复用已有的新鲜度(fresh)机制判定是否同一份,已确认且仍新鲜的直接用、不再问;身份绑定了筛选参数与文件内容的 sha256,所以**人工一旦改了文件,身份失效、会重新确认**——这正好接住"人工要改"的初衷。

评估侧加了自动确认开关:批量评估时直接当作已确认、旁路掉暂停,否则所有经过筛选的用例都会卡住。同时单独写了关闭自动确认才跑的 HITL 用例,验证三件事:确认前确实停住且未调用后续分析工具、确认后读取现成(可能被改过的)文件且不重跑筛选、表达模糊时反问而非猜测。

## 七、一个被这次改动揭开的事实:覆盖守卫此前是软停

实现上面的硬停机制时,发现了一件之前没意识到的事:单轮 A 类收敛所依赖的覆盖守卫,它的"无覆盖就不继续",**此前其实是提示词软停,不是代码强制**。工具层会返回 `needs_input`,system prompt 也写了"收到这个就停止",但工具记录层并没有在收到 `needs_input` 后终止本轮——也就是说,模型理论上仍可以继续往下调工具,只是此前多数情况靠提示词和模型行为停住了。

这意味着 A 类那条"11 → 0"的收敛,地基比当时以为的软:它当时能成立,垫的是模型的自觉,不是代码保证。这不否定当时的方向(把守卫返回 `needs_input` 焊进工具层是对的),但"返回之后真的不往下走"这最后一厘米,落在了提示词上。

本次为筛选确认新建的控制异常硬停机制,正好是补这最后一厘米的通用件。后续应把覆盖守卫的 `needs_input`/`no_data` 也用同一机制焊成代码硬停,把 A 类收敛从"靠模型自觉"升级为"代码强制"。这一项已记入待办,本轮范围只覆盖筛选确认。

记录这一点,是因为它本身就是评估方法的一部分:做一项新能力时反过来照出了既有机制的真实强度——而不是停留在"看起来已经解决了"。

## 八、贯穿全程的方法论

1. **先聚类再修,不全量修。** 一个根因常驱动一堆失败(A 类一个缺失的前置检查占了 73% 的失败)。聚类是为了找到杠杆、获得干净的因果归因、做结构性修复而非逐个贴症状,并能在边际收益递减时停下。
2. **修复有层次:提示词 → 代码 → 执行层。** 提示词能改变行为倾向,但确定性约束要焊进代码,且要焊在逻辑真正执行的那一层。
3. **单次通过不可信,记录可复现条件。** 评估结果随运行波动,每次运行记录模型、参数、时间、token、用例版本,结果才可复现、可对比。
4. **自动判官必须先对齐。** 用注入测试或人工标注验证判官能抓出已知失败,才敢信它、才敢以后不看。
5. **先观测再改。** 面对黑盒操作(如压缩),先让它的内部状态可见,再基于看见的事实动手,而不是基于推测。
6. **先有被测对象,再写测试。** 能力还没做时,对应的测试只占位、不写实。
7. **区分回归来源。** 一个失败要分清是本次改动引入的,还是本来就存在的——用压缩开/关对照、用自动判分的前后对比来隔离。
8. **新能力会反照既有机制的真实强度。** 做筛选确认的硬停时,才照出覆盖守卫此前是软停。每加一项能力,顺带重新审视它依赖的旧机制,而不是默认"之前那块已经解决了"。

## 九、边界与未决项

评估"够好"的标准不是零失败,而是:主要场景已覆盖、主要失败类已收敛、剩余失败都已被识别并主动归类。当前处于这个状态。以下为已识别、暂未处理的项:

- **路由过度调用**:专注单一分析时,偶尔误调降雨分析等无关工具(多个用例上重复出现)。已由自动判分稳定捕获,待单独修。
- **覆盖守卫硬停化**(高优先):覆盖守卫的 `needs_input`/`no_data` 目前仍是提示词软停。应复用筛选确认的控制异常机制焊成代码硬停,加固 A 类收敛。
- **`run_python` 绕过筛选确认**:`run_python` 暴露的加载函数仍读默认筛选文件,会绕过确认。已知遗留缺口,待单独处理。
- **system.md 中的真实点位示例**:示例用了真实点位名(W4/W6)与真实日期,是压缩 bug 的远端诱因。约束提取已不从 system prompt 取,当前安全;待整理文档时把示例改为占位符。
- **单轮 B/C/D 类零散失败**:低频的标签、措辞、指令遵循问题,已归档。
- **自动判分与人工标注的持续对齐**:当前靠注入测试验证,规模扩大后需建立自动判分与人工判定的一致率监控。
